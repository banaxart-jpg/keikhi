# Claude Code 用 BaaS（仮称: Claude Studio）設計ドラフト v1

> このドキュメントは Claude Code と一緒に要件を詰めるための**叩き台**。最終仕様ではない。

---

## 1. プロダクト概要

### 一言で
**「初回ハンドシェイクだけ自動化、あとは Claude Code に話しかけるだけで自分専用のミニアプリが増える」GCP ベース BaaS スターターキット**

### 解決する課題
- Vibe coding / ノーコードで個人や中小企業が業務アプリを作りたいが、**インフラ（Auth, DB, デプロイ, 認証, ストレージ）の初期構築が高い壁**
- Vercel / Bolt / Lovable はフロント特化、本格運用するとバックエンドが弱い・所有感がない
- Firebase / Supabase は BaaS だが、**Claude Code 前提のドキュメント構造（CLAUDE.md など）が無い** → AI に「読ませて動かす」設計じゃない
- 既存スタックの組み合わせと配線を毎回ゼロからやるのは中小企業には非現実的
- さらに副次的価値: **DX 人材育成・リスキリングの教材としても破壊力がある**（§13 詳述）。実プロジェクト駆動学習 + Claude Code 先生役 + 自動成長トラッキングで、既存のプログラミング教育を陳腐化させる潜在力

### 何を売るか
1. **テンプレートリポジトリ**（Cloud Run + Cloud SQL + Firebase Hosting + Auth + Cloud Tasks + Gemini/Claude/GPT 連携の完成形）
2. **Setup Wizard**（GCP プロジェクト作成・IAM・Secret・トリガ・DB ブートストラップを 5 分で完了する CLI or Web）
3. **CLAUDE.md / DEPLOY.md テンプレ**（Claude Code が読んで自律的に動ける文書群）
4. **スターターパック**（経費・会議・請求書など実用ミニアプリの雛形）
5. **ノウハウ**（ハマりポイント集、過去事故の再発防止メモ）

## 3. プロダクト構成

### 3-1. テンプレートリポジトリ
- GitHub Template として配布
- 構成は現 `keihi` リポをサニタイズしたもの:
  - `apps/index.html` (ランチャー)
  - `apps/cost/` (AIコスト計算サンプル、認証だけのシンプル系)
  - `apps/<sample>/` (経費アプリの汎用版を1本サンプルとして同梱)
  - `apps/keihi/server/` (Cloud Run コード、汎用化された API)
  - `apps/keihi/infra/schema.sql` (DB スキーマ、初期サンプル)
  - `apps/keihi/cloudbuild.yaml` (Cloud Build トリガ定義)
  - `infra/bootstrap.sh` (1コマンドでスタック作成)
  - `infra/db.sh` (Cloud SQL 接続ラッパー)
  - `infra/deploy-hosting.sh` (緊急時手動デプロイ)
  - `CLAUDE.md` (Claude Code 用の振る舞い指定テンプレ)
  - `DEPLOY.md` (デプロイ構造の完全ドキュメント)
  - `README.md` (人間向け全体像とミニアプリ実装レシピ)

### 3-2. Setup Wizard

**フロー（5 分目標）**:
1. ユーザーがランディングページで「始める」ボタン
2. Google アカウントで OAuth ログイン（GCP 操作の同意取得）
3. ウィザード画面で質問:
   - プロジェクト名（英数字、unique チェック）
   - 想定リージョン（asia-northeast1 デフォルト）
   - 想定する最初のアプリの種類（経費 / 請求書 / 会議 / 白紙）
   - 招待したいメンバーのメールアドレス（任意）
4. バックエンドで以下を自動実行:
   - GCP プロジェクト作成（請求アカウントとリンク）
   - 必要 API 有効化（Cloud Run, Cloud SQL, Cloud Build, Hosting, Firebase Auth, Secret Manager, Vertex AI, Cloud Tasks）
   - 組織ポリシー上書き（必要なら `iam.allowedPolicyMemberDomains` 等）
   - Cloud SQL インスタンス作成 + DB 初期化（schema.sql apply）
   - Cloud Storage バケット作成
   - Artifact Registry 作成
   - Service Account 作成 + IAM 設定
   - Secret Manager に Gemini API key 投入（ユーザーが BYOK or 共有キー）
   - Firebase プロジェクト初期化 + Hosting site 作成 + Auth プロバイダ有効化
   - GitHub Template からユーザーの GitHub リポにフォーク（or Wizard 側にホスティング）
   - Cloud Build トリガ作成（GitHub 連携）
   - 初回 push → 自動デプロイ → 稼働確認
5. 完了画面で「あなたのアプリが立ち上がりました」+ URL + 「これから Claude Code に話しかけてミニアプリを増やしていけます」案内

### 3-3. スターターパック

各アプリは「git clone してそのまま動く」形で同梱:
- **経費管理** (領収書 OCR + 記録)
- **請求書管理** (支払い / 入金管理)
- **会議録** (3者 AI 議論からの結論抽出)
- **顧客管理** (シンプル CRM)
- **日報** (LINE 連携)
- **見積もり** (PDF 生成)
- **空のミニアプリ雛形** (自分でゼロから作る用)

### 3-4. CLAUDE.md テンプレ

各ユーザーが自分のリポに持つ CLAUDE.md は、現プロジェクトの CLAUDE.md をベースにテンプレ化:
- 触っちゃダメリスト
- push 手順
- ハマりポイント集
- （オプション）育成チェックリスト形式の「学習トラッカー」

ユーザーは Claude Code に「README とか CLAUDE.md 読んで、〇〇を作って」と言うだけ。

## 4. アーキテクチャ

### 4-1. ユーザーのアプリ側（テナント側）
```
┌──────────────────────────────────────┐
│ ユーザーの GCP プロジェクト（顧客所有）          │
│                                      │
│  ┌─────────────────────────────┐   │
│  │ Firebase Hosting (静的フロント配信)  │   │
│  └──────────────┬──────────────┘   │
│                 │                    │
│                 ▼                    │
│  ┌─────────────────────────────┐   │
│  │ Cloud Run (API 実行基盤)        │   │
│  │   - express, multi-LLM 連携      │   │
│  │   - 認証ミドルウェア (Firebase Auth) │   │
│  └──────────────┬──────────────┘   │
│                 │                    │
│        ┌────────┼────────┬────────┐  │
│        ▼        ▼        ▼        ▼  │
│   Cloud SQL  Storage  Tasks   Secrets │
└──────────────────────────────────────┘
```

**重要**: ユーザーの全資産は**ユーザー自身の GCP プロジェクトの中**。我々はテンプレと Wizard を売るだけで、顧客データには触れない。

### 4-2. 我々のサービス側（Studio 本体）
```
┌──────────────────────────────────────┐
│ Studio 運営側 GCP プロジェクト                │
│                                      │
│  ┌─────────────────────────────┐   │
│  │ LP + Wizard UI (Next.js)       │   │
│  │   - サインアップ / プラン管理      │   │
│  │   - GCP OAuth フロー            │   │
│  │   - Wizard 実行画面            │   │
│  └──────────────┬──────────────┘   │
│                 │                    │
│                 ▼                    │
│  ┌─────────────────────────────┐   │
│  │ Wizard Worker (Cloud Run)      │   │
│  │   - gcloud / firebase コマンド    │   │
│  │     orchestration             │   │
│  │   - GitHub API でテンプレ clone │   │
│  │   - 状態追跡 (進捗・エラー)        │   │
│  └──────────────┬──────────────┘   │
│                 │                    │
│                 ▼                    │
│  ┌─────────────────────────────┐   │
│  │ メタデータ DB (Postgres)         │   │
│  │   - 顧客一覧、プラン、課金状態     │   │
│  │   - Wizard 実行ログ            │   │
│  └─────────────────────────────┘   │
│                                      │
│  ┌─────────────────────────────┐   │
│  │ Stripe (課金)                  │   │
│  └─────────────────────────────┘   │
└──────────────────────────────────────┘
```

### 4-3. データ所有権モデル
- **顧客資産**: 全部顧客の GCP プロジェクト内（コード・DB・Storage・Secret）
- **我々が持つ情報**: アカウント情報・プラン・課金状態・Wizard 実行ログ・サポート問い合わせ履歴
- **GCP 課金**: 顧客直接負担（顧客の請求アカウントから引き落とし）
- **我々への支払い**: テンプレ + Wizard + サポートの月額

**法務的な切り分け**: 顧客データは我々のサーバーを通過しない設計。Wizard は OAuth トークンで顧客の GCP を操作するが、初回セットアップ後は接続切断。これで GDPR / 個人情報保護法のリスクを最小化。

## 7. 競合分析

| 競合 | 同じ | 違う | 強み | 弱み |
|---|---|---|---|---|
| **Vercel** | デプロイ自動化 | フロント特化、Edge Network | UI 滑らか | バックエンド弱い、所有感薄い |
| **Bolt.new** | コード自動生成 | フルスタック SaaS | 即動く | 本格運用と所有移管が難しい |
| **Lovable.dev** | AI で作る | デザイン重視 | UI が綺麗 | バックエンド弱い、英語圏 |
| **v0 (Vercel)** | UI コード生成 | コンポーネント特化 | shadcn/ui 統合 | アプリ全体じゃない |
| **Firebase Studio (Google)** | BaaS + AI | Google 純正、無料枠厚い | 強力 | Claude Code 連携なし、UI 重い |
| **Supabase** | BaaS | OSS / Postgres 純粋 | 開発者向け | 中小企業や非エンジニア向きじゃない |
| **Heroku / Render** | デプロイ | 旧世代、AI 連携なし | 安定 | モダンじゃない |

### 我々の差別化
1. **Claude Code 前提のドキュメント構造**（他社にない）
2. **GCP マルチサービス連携の完成形**（Cloud Run + Cloud SQL + Hosting + Tasks + Vertex AI + Auth）
3. **顧客 GCP プロジェクトに資産を残す**（所有感、ベンダーロックイン回避）
4. **日本市場 / 中小企業特化**（英語圏競合に対する地の利）
5. **複数 LLM 連携テンプレ**（Gemini / Claude / GPT を同時に使える）

## 9. 技術的な未解決論点

Claude と詰めたいポイント:

1. **Wizard の実装方式**
   - A: Web UI + サーバー側で gcloud SDK 呼ぶ（自社管理）
   - B: Cloud Shell ベース（ユーザー自身の Cloud Shell で実行、我々は手順とスクリプトのみ提供）
   - C: ハイブリッド（B からスタート、Pro プランで A を提供）

2. **GitHub リポジトリの扱い**
   - A: ユーザーの GitHub に Template fork
   - B: 我々がホスティング（Wizard でユーザー専用リポ作成）
   - C: ユーザーは Git を意識しない（Cloud Source Repository or GitLab 内蔵）

3. **マルチテナント or プロジェクト分離**
   - 今の設計はプロジェクト分離（顧客ごとに別 GCP プロジェクト）
   - マルチテナント化（1つの GCP プロジェクトで複数顧客を相乗り）の方が運用安いが、所有感が消える
   - → プロジェクト分離が正解だが、Free プランだけマルチテナントで提供する手も

4. **LLM キーの管理**
   - A: 全顧客が BYOK（自分の Anthropic / OpenAI / Google アカウントでキー作って入れる）
   - B: 我々が共有キーで提供（利用量ベース転嫁）
   - C: ハイブリッド（Free は共有、Pro 以上は BYOK）

5. **アップデート配信**
   - テンプレを更新した時、既存顧客のリポにどう取り込ませるか
   - A: Wizard で「更新を取り込む」ボタン（merge conflict は手動）
   - B: 各テンプレを GitHub Releases で配って、ユーザーが cherry-pick
   - C: Pro 以上は我々がアップデート PR を顧客リポに自動送信

6. **CLAUDE.md のバージョン管理**
   - 各テンプレに同梱する CLAUDE.md は我々のメンテ対象だが、ユーザーが自分のルールを追加することもある
   - → セクション分離（"我々の標準" / "あなたのカスタム"）の構造設計が必要

7. **データベース移行・バックアップ**
   - 顧客が「やめる」「他社に乗り換える」と言った時のエクスポート機能
   - → 標準で `infra/dump.sh` 同梱 + DB ダンプ DL ボタンを管理画面に

8. **マーケットプレイス（他社テンプレ）の品質管理**
   - 誰でも投稿できると質が落ちる
   - → 審査制 / レビュー制 / 我々が認証したテンプレマーク

9. **「学習トラッカー（系統 A/B チェックリスト）」を商品にするか** → **§13 で詳述、独立商品ラインとして本格展開する想定**
   - 現プロジェクトの CLAUDE.md §7 にある「育成チェックリスト」はユニークな差別化要素
   - Team プラン特典として「メンバー育成トラッカー」を組み込み
   - さらに教育機関 / DX 人材育成 / リスキリング向けに独立商品化
   - Claude が学習者のコミットや会話から成長を自動判定 → ダッシュボードで可視化
   - 教育コンテンツ事業として、SaaS 本体より高単価帯を狙える

10. **国際展開**
    - 日本市場で証明 → アジア → 欧米
    - i18n をいつから入れるか

## 12. Claude と詰めたい優先順位

このドキュメントを見せて、Claude に以下を聞くと議論が進む:

1. 「§9 の論点について、それぞれ A/B/C どれが筋いいと思う？」

## 13. 教育・人材育成プラットフォームとしての価値（隠れた本命）

このスタックが「アプリ開発スターターキット」という枠を超えて、**ソフトウェア開発 / DX 推進人材を育てる教材としても破壊的に強い**。実プロジェクト (BANAX 内部) でその効果が観測済み。

### 13-1. なぜ教材として強いか

| 既存の学習方法 | 限界 |
|---|---|
| Progate / ドットインストール | 完結する課題はやるが、**本物の運用感覚が身に付かない** |
| プログラミングスクール | 数十万円、期間半年〜1年、**実環境のデプロイは触らせない** |
| 本 / Udemy | 受動的、書いた通りに動かしても**応用できない** |
| 個人開発 | 環境構築でつまずく、デプロイ・認証・DB で**95% が脱落** |

**このスタックなら**:
- 初回ハンドシェイクは Wizard で 5 分（壁を消す）
- **本物のクラウド (GCP) + 本物の AI (Gemini/Claude/GPT) + 本物のデプロイ (Cloud Build)**
- Claude Code が**翻訳・例え話・先生役**として常駐
- **失敗事例（過去ハマりポイント、ロールバック、CORS 事故）も学べる**
- 「自分の業務に直結するアプリ」を作るので**学習意欲が消えない**
- 1 ヶ月で「自分のアプリを 1 個本番運用」が現実的

### 13-2. ユーザーの知識レベル測定機能（学習トラッカー）

CLAUDE.md §7 にある **「系統A（作る軸）」「系統B（直す軸）」のチェックリスト構造**を商品化:

**仕組み**:
- 各プラン契約時に「学習トラッカー」が自動同梱
- ユーザーが Claude Code を使うたびに、コミットや会話から**Claude 自身が成長を観測** → チェックリストに勝手に印を付ける
- 育成側（マネージャー / 学校 / 親）はダッシュボードで進捗を見られる
- 月 1 でスキル評価レポート自動生成

**チェックリストのカテゴリ例（系統A・系統B 流用）**:
- Level 1: Web の全体像（mental model）
- Level 2: API
- Level 3: データベース
- Level 4: AI / LLM の構造
- Level 5: このプロジェクト固有の構造
- Level 6: Claude Code を使ったアプリ開発
- Level 7: コスト・運用感覚
- Level 8: セキュリティ意識
- Level 9: コミュニケーション
- Level 10: エンジニアとしての完成度

**判定基準**: 「Claude が説明して "わかった" と返した」は不可。「自発的にコードで使った / 自分の言葉で他人に説明した / 例え話に翻訳した」を判定根拠とする（受動理解は除外）。

**特長**:
- **教育者ガイドが裏で動く**: 学習者本人には「評価されてる」と意識させず、自然なコード活動から判定 → モチベ低下を防ぐ
- **過小評価方針**: 確証あるものだけチェック → 後から客観的に「実力ある」と言える

### 13-5. なぜ「測定」が刺さるか

中小企業の経営者が一番欲しいのは「**この社員、本当に IT スキル付いてるのか？**」の客観評価:
- 自社の DX 推進担当が「やってます」と言うが、実力が見えない
- 給与改定の根拠が欲しい
- 採用時のスキル評価基準が欲しい

→ **学習トラッカーが「客観評価ツール」として独立した商品価値**を持つ。アプリ作成 SaaS と組み合わせると相乗効果。

### 13-6. ロードマップへの組み込み

**Phase 1 (1〜3ヶ月)**: 
- 学習トラッカー MVP を Pro / Team プランに同梱（Phase 1 Wizard と同時実装）
- ベータユーザーに「うちの社員 X さんがどこまで成長したか見られます」と訴求

**Phase 2 (3〜6ヶ月)**: 
- ダッシュボード UI（マネージャー向け）
- 月次レポート自動生成
- 教育機関向けデモ営業開始

**Phase 3 (6〜12ヶ月)**: 
- **教育機関ライセンス**を別商品として独立
- **DX人材育成パック**を BANAX 等の事例ベースで売る
- プログラミングスクール / SES へのライセンス販売
- 教育系のメディア露出（経済産業省 DX 関連、業界紙）

### 13-7. ストーリー販売

実例 = 楓ちゃん（BANAX の名取）が IT 初心者から **3 週間で seikyu アプリ本番運用** に到達した話を**ケーススタディとして公開**:
- 「建設業の事務員が、半年で自社の社内システムを自分で増やせるようになった」
- 「外注で月 50 万円かかってたツールを内製化、年間 600 万円削減」
- ストーリーとしてもメディアに刺さる

### 13-8. 教育・育成版の差別化メッセージ

**「教える」じゃなく「育つ環境を渡す」**

- 既存の教育商品は「知識を詰め込む」発想
- このスタックは「**自分の業務に必要なアプリを Claude Code と一緒に作るうちに、結果的にプロになる**」設計
- 学習者は「学習している」と思わず、業務改善している感覚のまま IT 人材になる
- トラッカーが**裏で**成長を測る（学習者本人は意識しない）

これは、**Linux Torvalds が独学でカーネル作ったような「実プロジェクト駆動学習」を制度化したもの**と言える。
